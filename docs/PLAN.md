# Boardy — 보드게임 AI 컴패니언

목표: 여러 보드게임을 함께 플레이하는 AI 플레이어를 만들고, 온라인에서 친구들과
실시간으로 그 AI와 함께 플레이할 수 있는 서비스를 구축한다. 첫 게임은 협력
트릭테이킹 카드게임 "The Crew: Mission Deep Sea" (저장소 내 슬러그: `deep_sea_crew`).

## 저장소 구조 (2026-08-08 리팩터링)

처음엔 `deep_sea_crew` 하나만 구현하면서 시작했지만, 이 저장소의 실제 목적은 여러
보드게임을 지원하는 것이라 구조를 다음과 같이 나눴다:

```
src/boardy/
  core/
    game_spec.py   게임이 구현해야 하는 최소 계약 (GameSpec dataclass)
    registry.py    슬러그 -> GameSpec 레지스트리 (게임 패키지를 import하면 등록됨)
  web/             게임에 무관한 공용 실시간 서비스 (FastAPI + WebSocket)
    rooms.py       Room이 GameSpec을 통해서만 게임 상태를 다룸 (카드/트릭 개념 모름)
    server.py      REST(`/api/rooms`, `/api/games`) + WS(`/ws/{code}`)
    static/        지금은 Deep Sea Crew 전용 프론트엔드 (아래 설명 참고)
  cli.py           `python -m boardy.cli --game <slug> ...` — 게임별 CLI에 위임
  games/
    deep_sea_crew/ 이 게임의 규칙 엔진 + AI 학습 파이프라인 + 자체 CLI 전부
      spec.py      engine.py 등을 GameSpec으로 감싸서 registry에 등록
      web_view.py  GameState -> 웹 프론트엔드가 기대하는 JSON 스키마 매핑
data/deep_sea_crew/tasks.json   이 게임의 과제 데이터 (placeholder, 아래 참고)
tests/deep_sea_crew/            이 게임의 테스트
```

**설계 원칙**: 트릭테이킹 게임의 카드/트릭/통신 같은 개념은 다른 장르 게임(예: 체스류)과
공유할 게 거의 없다. 그래서 게임 엔진·AI·상태 표현은 게임마다 완전히 독립적으로 두고,
`boardy.web`/`boardy.cli` 같은 호스트 레이어가 실제로 필요로 하는 좁은 경계만
`GameSpec`으로 표준화했다: 새 게임을 시작, 좌석별 합법수 조회, 액션 적용, 차례/종료
조회, 좌석별 JSON 뷰 렌더링. 액션은 항상 문자열이라(카드 코드 등) 내부 액션 타입이
무엇이든 경계가 단순하게 유지된다. 프론트엔드(`static/`)는 아직 Deep Sea Crew 전용
UI지만, 그 응답 스키마(hand/legal_moves/trick_in_progress/tasks/...)는 "손패 형태의
토큰 + 목표 목록" 형태의 다른 카드게임이라면 상당 부분 재사용 가능하도록 잡아뒀다 —
체스처럼 완전히 다른 형태의 게임엔 안 맞고, 그건 그때 가서 별도 프론트엔드가 필요함.

새 게임 추가 방법: `src/boardy/games/<slug>/`에 규칙 엔진 구현 → `spec.py`에서
`GameSpec`으로 감싸 `register()` 호출 → `games/__init__.py`에서 import 한 줄 추가.

## 알려진 사실 / 가정 (Deep Sea Crew, 검증 필요)

웹 검색으로 확인된 것:
- 2~5인용 협력 트릭테이킹 카드 게임 (전작 "Quest for Planet Nine"의 후속작)
- 색상(스위트) 카드 1~9 + 잠수함(트럼프) 카드
- 통신은 Sonar 토큰으로 카드 한 장을 공개하고 최고/최저/유일 표시
- "Currents", "Rapture of the Deep" 같은 특수 미션 심볼이 통신 제한/허용을 바꿈
- 과제 카드는 96종 (본가 박스 기준 통상 알려진 수치)

**가정하고 우선 구현한 것** (나중에 실제 룰북/카드 사진으로 교정 예정):
- 색상 4개 × 1~9 = 36장, 잠수함(트럼프) 1~4 = 4장, 총 40장
- 플레이어 3~5인 지원 (사용자 최우선 시나리오: 3인이서 4인 밸런스를 흉내내기 위해 AI 1명 참여)
- 커뮤니케이션: 게임당 1회, 카드 1장 공개 + (최고/최저/유일) 마커
- 과제(Task)는 하드코딩된 96개 실제 카드 텍스트 대신, 데이터 기반 DSL
  (`data/deep_sea_crew/tasks.json`)로 절차적으로 표현. 조건 타입: `win_card`,
  `win_trick_number`, `win_exact_count`, `never_win_color`, `win_no_tricks` 등.
  실제 카드 96장 텍스트를 확보하면 이 파일만 교체하면 됨.

이 가정들은 실제 룰북 사진/텍스트를 사용자가 제공하면 빠르게 교정 가능하도록
로직과 데이터를 분리해서 설계함.

## 단계별 계획 (Deep Sea Crew 기준)

### Phase 1 — 규칙 엔진 (CLI) ✅ 완료
- `src/boardy/games/deep_sea_crew/cards.py`: 카드/덱
- `.../tasks.py`: 과제 DSL + 완료 판정
- `.../communication.py`: Sonar 토큰 통신
- `.../engine.py`: 게임 상태, 트릭 해석, 합법수 생성, 승패 판정
- `.../missions.py`: `data/deep_sea_crew/tasks.json` 템플릿으로 실제 미션 생성
- `.../cli.py`: 사람 vs 랜덤봇 CLI 대화형 플레이
- `tests/deep_sea_crew/`: pytest (20개 통과)

### Phase 2 — AI 플레이어 학습 ✅ 파이프라인 완료, 학습 신호는 아직 미검증
채택한 구조:
1. **학습**: `mcts.py`의 `run_mcts`가 실제(oracle) `GameState` 위에서 표준 PUCT 탐색을 돈다 —
   협력 + 순차턴(한 번에 한 명만 행동) 게임이라 제로섬 minimax의 부호 반전이 필요 없고,
   그냥 공유 스칼라 가치(미션 성공 확률)를 트리 위로 그대로 backup하는 단일 에이전트
   MCTS로 축소됨. 신경망은 노드마다 항상 "행동할 좌석 하나의" 부분정보 인코딩만 보고
   정책/가치를 예측하므로, 탐색 자체는 치팅해도 신경망은 은닉정보 없이 일반화하도록 학습됨.
2. **실전 추론**: `mcts_inference.py`의 `run_ismcts`가 여러 개의 "determinization"
   (공개 정보 — 지금까지 낸 카드, 트릭 위 카드, 공개된 Sonar 신호, 그리고 트릭 규칙상
   특정 색을 안 따라간 사람은 그 색이 없다는 표준 추론)에 부합하는 손패 배치를 무작위로
   샘플링해 각각에 대해 `run_mcts`를 돌리고, 루트의 방문 횟수를 모아 최종 정책으로 사용.
3. 구현체: `encoding.py`(자기중심 특징 인코딩), `network.py`(PyTorch MLP, 정책 헤드
   40장 카드 + 가치 헤드 시그모이드), `self_play.py`, `train.py`(자기대국 → 리플레이
   버퍼 → 학습 → 체크포인트 저장 루프), `evaluate.py`(RandomPlayer 대비 미션 성공률
   비교).
- 범용 alpha-zero-general 라이브러리는 2인 제로섬/완전정보 가정이 강해 그대로 못 쓰고,
  위 구조를 직접 구현함 (체스/바둑/오델로류 완전정보 게임엔 적합하지만 이 프로젝트엔 부적합).
- 보상: 미션(과제 세트) 전원 성공 시 1.0, 하나라도 실패 시 0.0 (팀 공유 가치).
- **1차 검증 결과 (2026-08-08)**: 3인/난이도6, 15 iteration × iteration당 15게임 ×
  시뮬레이션 25회짜리 스모크 학습을 CPU로 돌려봄 (`checkpoints/`, gitignore됨).
  가치망 손실(value_loss)은 0.5→0.02대로 잘 떨어졌지만, 이건 대부분 "거의 항상 실패"라는
  패턴을 외운 것에 가까움 — 정책 손실(policy_loss)은 거의 안 줄었고, 학습된 AI(ISMCTS
  탐색 포함)의 실제 성공률도 6.7%로 랜덤(3.3%)과 표본 30게임 기준 통계적으로 구분 안 됨.
  파이프라인 자체(자기대국→학습→체크포인트→ISMCTS 추론→평가)는 끝까지 정상 동작 확인.
- **2차 검증 결과 — 쉬운 난이도 대조 실험 (2026-08-08)**: 난이도를 1로 낮춰서(랜덤
  플레이어 기준 성공률 ≈23%, 난이도6의 ≈1.5%보다 훨씬 관측하기 쉬움) 20 iteration ×
  게임 20개 × 시뮬레이션 30회로 재학습(`checkpoints_easy/`, gitignore됨) 후, 학습
  효과와 탐색(search) 효과를 분리하기 위해 4가지를 비교:
  | 조건 | 성공률 |
  |---|---|
  | 랜덤 플레이어만 | 18~26% (n=60~100) |
  | 학습망, 탐색 없이 그리디 정책만 | 23% — 랜덤과 구분 안 됨 |
  | **학습 안 된** 신경망 + ISMCTS 탐색 | 31.7% (n=60) |
  | **학습된** 신경망 + ISMCTS 탐색 | 26.7% (n=60) |

  **결론**: 탐색(MCTS/ISMCTS) 자체는 확실히 유효함 — 학습 안 된 랜덤 초기화 망을 붙여도
  탐색만으로 랜덤 대비 성공률이 오름. 반면 신경망이 자기대국 학습으로 뭔가 유용한 걸
  배웠다는 증거는 아직 없음 (학습된 쪽이 오히려 조금 낮게 나왔지만 n=60이라 오차범위 안).
- **3차 시도 — 대규모 재학습 (2026-08-08, 중단됨)**: 60 iteration × 게임 30개 ×
  시뮬레이션 50회(3단계로 나눠 진행 예정, 총 2.5시간 추정) 학습을 시작했으나, 사용자가
  이 시점에 저장소를 다중 게임 구조로 리팩터링해달라고 요청. 모듈 경로가 바뀌는 리팩터링과
  충돌할 게 뻔해서(재개 시 어차피 새 경로로 다시 실행해야 함) 초반(iteration 1개 완료
  전)에 중단하고 리팩터링을 먼저 진행함. **리팩터링 이후 재개 필요** — 명령어는
  `python -m boardy.games.deep_sea_crew.train ...`로 바뀜, `checkpoints_big/`은
  비어있거나 미완성 상태.
- **다음에 학습을 재개한다면**: (a) 위 대규모 학습을 새 경로로 재시작, (b) 신경망
  크기·러닝레이트 등 하이퍼파라미터 튜닝, (c) GPU 사용 여부 검토, (d) 자기대국 시뮬레이션
  수 자체를 늘려 학습 타겟(정책 분포) 품질을 높이는 것도 고려.

### Phase 3 — 실시간 온라인 플레이 서비스 ✅ 뼈대 완료 (+ 다중 게임 호스팅으로 일반화)
- `src/boardy/web/rooms.py`: 인메모리 Room/좌석 관리. **GameSpec을 통해서만** 게임 상태를
  다루므로 카드/트릭 같은 개념을 전혀 모름 — 다른 게임이 등록되면 그대로 호스팅 가능.
  사람=WebSocket, AI=`spec.make_random_player`/`make_smart_player`. 단일 프로세스 전제,
  재연결/영속화는 아직 없음 — 스켈레톤 단계라 의도적으로 단순하게 둠.
- `src/boardy/web/server.py`: FastAPI. `GET /api/games`로 등록된 게임 목록, `POST
  /api/rooms`로 (게임 슬러그 지정해) 방 생성, `/ws/{code}` WebSocket으로
  join/add_ai/start/play/communicate 메시지 처리 (액션 페이로드 키는 게임 무관하게
  `action`). AI 차례는 서버가 자동 처리.
- `src/boardy/games/deep_sea_crew/web_view.py`: `GameState` -> 웹이 기대하는 JSON
  스키마로 매핑 (이 파일이 GameSpec.serialize_seat 구현체 — 게임별 지식이 여기 있음).
- `src/boardy/web/static/`: React 대신 순수 HTML/CSS/JS 스켈레톤 (npm 툴체인 없이 바로
  구동 가능하게 하려는 선택). 지금은 Deep Sea Crew 전용 UI (카드 코드/색상 렌더링 등).
- `src/boardy/games/deep_sea_crew/ai.py`: AI 좌석용 공유 `PolicyValueNet` 싱글턴
  (checkpoints_easy/ → checkpoints/ 순으로 체크포인트 탐색, 없으면 학습 안 된 망으로
  폴백 — 위 대조실험대로 탐색 자체가 랜덤보다 강하므로 이래도 의미 있음). 로비에서 AI
  추가 시 랜덤/스마트(탐색) 선택 가능. 스마트 AI의 ISMCTS 탐색은
  `loop.run_in_executor`로 돌려 다른 연결을 막지 않도록 함.
- 브라우저로 방 생성 → AI 2석 채움(랜덤+스마트 혼합) → 게임 시작 → 합법수만 클릭 가능 →
  AI 턴 자동 진행 → Sonar 통신 → 미션 종료 배너까지, 리팩터링 이후 구조로 전체 플로우
  재검증 완료 (2026-08-08).
- **아직 안 한 것**: 재연결/방 목록/영속 저장소, 모바일 반응형, React 전환 여부 결정.
  (2026-08-08 업데이트: 프론트엔드 게임 선택 UI는 Gomoku 추가하면서 같이 구현함 — 아래
  Phase 4 참고.)

## Phase 4 — Gomoku (두 번째 게임): 진짜 AlphaZero ✅ 완료, 학습은 진행 중

Deep Sea Crew는 협력+불완전정보라 AlphaZero를 억지로 변형해서 썼지만, Gomoku(오목)는
정반대로 골랐다 — 진짜 2인 제로섬 완전정보 게임이라 표준 AlphaZero 자기대국이 그대로
들어맞는지, 그리고 `GameSpec` 경계가 완전히 다른 종류의 게임에도 실제로 잘 작동하는지
검증하는 목적.

- `board.py`/`engine.py`: 9×9 보드, 5개 연속이면 승리 (Renju식 흑 금수 없음). 15×15/19×19
  대신 9×9를 고른 건 CPU로 실제 학습이 끝나는 규모여야 해서.
- `network.py`: 작은 CNN (conv 3블록 + 정책/가치 헤드), 입력 평면 4장(내 돌, 상대 돌,
  마지막 수, 흑/백 차례 표시).
- `mcts.py`: 진짜 2인 제로섬 PUCT — 각 노드의 평균 가치는 "그 노드에서 둘 차례인
  사람" 관점으로 저장되고, 한 수 위로 backup할 때마다 부호가 반전됨(`value = -value`).
  그래서 자식 선택 시 점수는 `-child.value`를 씀 (자식의 가치는 부모 입장에서 보면
  상대方 관점이므로). 4목이 완성된 상황을 일부러 만들어서 탐색이 승리 완성수를
  실제로 찾아내는지 테스트로 검증함.
- `self_play.py`/`train.py`/`evaluate.py`: Deep Sea Crew와 같은 자기대국→리플레이
  버퍼→학습→체크포인트 구조지만, 가치 타깃이 게임 전체에서 하나가 아니라 수마다
  부호가 바뀜(그 수를 둔 사람 기준 +1/-1/0).

### 학습 결과 — gatekeeping의 중요성을 직접 발견함 (2026-08-08)

1차: 15 iteration × 게임 25개 × 시뮬레이션 100회, gatekeeping 없이(매 iteration 무조건
최신 가중치 승격) 학습. `policy_loss`가 4.14→3.18로 꾸준히 줄어서(균등분포 기준선
ln(81)≈4.39) 학습 자체는 되고 있었음. 랜덤 상대로는 학습망/학습안된망 둘 다 95%
승률(38/40) — 오목은 탐색 자체가 워낙 강해서 랜덤 상대로는 천장 효과가 남.

**진짜 비교는 학습망 vs 학습안된망 직접 대결**(탐색 80회, 온도 0.5로 실제 확률적
독립 대국 30판): **학습망 9승 — 학습안된망 21승**. 학습된 쪽이 통계적으로 유의하게
더 약했음(이 정도로 치우칠 확률 ≈1.5%, 우연이 아님).

**원인**: 학습안된 망은 사실상 균등분포 prior라 PUCT 탐색이 넓게 퍼지고, 오목은 탐색
중 실제 승패가 정확히 확인되는 게임이라 이것만으로도 충분히 강함. 반면 15 iteration
(자기대국 375판)짜리 학습망은 "애매하게 확신에 찬" prior를 갖게 됐는데, 그 확신이
아직 정확하지 않아서 오히려 얕은 탐색 예산에서 탐색을 나쁜 방향으로 좁힘. 더 근본적인
원인은 **gatekeeping 부재** — 매 iteration마다 무조건 승격시키다 보니 일시적 후퇴를
감지·차단할 방법이 없었음. 원조 AlphaZero 논문도 정확히 이 문제 때문에 "새 망이 기존
최강 망을 실전에서 과반 이상 이겨야만 승격" 하는 평가 단계를 둠.

**수정**: `evaluate.arena(candidate, incumbent, ...)` 추가, `train.py`가 이제
`best.pt`(gatekeeping 통과한 망, 자기대국에도 이걸 씀) vs 후보(`net`, 매 iteration
학습됨)를 매번 12판 아레나 대국으로 겨루게 하고, 후보가 이겨야만(승수>패수) 승격,
아니면 후보를 `best.pt`로 리셋. `ai.py`도 `best.pt`를 우선 사용하도록 변경.
기존(gatekeeping 없이 학습된) 체크포인트는 위 실험대로 학습 안 된 것보다 못하다는 게
증명됐으므로 `checkpoints_gomoku/`를 비우고 gatekeeping 파이프라인으로 처음부터 재학습.

**2차 — gatekeeping 포함 대규모 재학습 (2026-08-08) ✅ 성공**: 80 iteration × 게임
25개 × 시뮬레이션 100회, 아레나 12판×시뮬레이션 80회. 27/80 iteration(~34%)만 실제
승격됨 — 나머지는 gatekeeping이 걸러낸 일시적 후퇴였다는 뜻. `policy_loss`가
4.17→2.93까지 떨어짐 (1차 시도의 3.18보다 훨씬 더 수렴).

**최종 검증**:
| 비교 | 결과 |
|---|---|
| 최종 학습망(`best.pt`) vs 랜덤 (시뮬레이션 150회, 30게임) | **30승 0패 (100%)** |
| 최종 학습망 vs **학습 안 된 망** 직접 대결 (시뮬레이션 80회, 온도 0.5, 30게임, 색 교대) | **23승 7패 (77%)** |

1차 시도(gatekeeping 없이 15 iteration)에서는 학습망이 학습 안 된 망에 9승 21패로
**졌던** 것과 비교하면 완전히 역전됨 — gatekeeping + 더 많은 반복이 실제로 유효했다는
확실한 증거. Deep Sea Crew 때와 달리 Gomoku는 "진짜 학습되고 있다"고 이제 자신 있게
말할 수 있음.

### 규칙 완성도 재점검 + GUI 대개편 (2026-08-09)

"규칙이 바뀌면 학습을 다시 시켜야 하니, 학습 시작 전에 규칙을 완벽히 정립한다"는
방침 아래 다음을 수정:

- **통신 타이밍 버그**: 트릭 진행 중에도 통신이 가능했던 것을 트릭 시작 전에만
  가능하도록 제한 (`GameState.communicate`가 `trick_in_progress`가 비어있지 않으면
  거부).
- **"정확히 N개"/"최소 N개" 과제 조기 실패**: 기존엔 마지막 트릭이 끝나야만 실패
  판정이 났음. 이제 남은 트릭 수로 봤을 때 수학적으로 달성 불가능/이미 초과한
  순간 즉시 실패로 확정 (`tasks.py`의 `check_after_trick`에 `remaining` 계산 추가).
- 과제 설명을 GUI에 한국어로 노출 (`Task.describe()`).
- Gomoku 보드를 9×9 → **15×15**(실제 크기)로 변경. 기존 9×9 체크포인트는 새
  네트워크와 구조가 안 맞아 삭제함 — **재학습은 사용자가 명시적으로 보류 요청,
  다시 요청 전까지 시작하지 않음**.
- **과제 배정 규칙 자체가 잘못됨**: "각 과제를 무작위로 한 플레이어에게 배정"은
  한 플레이어가 과제를 여러 개, 다른 플레이어는 하나도 못 받는 경우가 생겨 오류.
  올바른 규칙(사용자 지적): 정해진 개수의 과제를 뽑아 공개하고, 선장부터 좌석
  순서대로 돌아가며 각자 원하는 과제를 한 장씩 드래프트. 엔진에 `phase`
  state machine(`"task_draft"` → `"playing"`) 도입, `draft_task()` 추가,
  CLI/self-play/evaluate/웹 모두 드래프트 루프를 거치도록 수정.
  `docs/deep_sea_crew_rules.md` "준비" 섹션도 갱신함.
- **GUI 전면 개편**:
  - 과제 드래프트 단계 자체를 화면에 표시 (누구 차례인지, 뽑을 수 있는 과제 목록).
  - 각 플레이어의 카드 더미(pile) 옆에 그 플레이어가 드래프트한 과제를 표시.
  - 트릭이 끝나면 승자를 명시적으로 보여주고 **"다음" 버튼을 눌러야만** 다음
    트릭으로 진행 (서버: `Room.awaiting_next` 플래그 + `acknowledge_next()`,
    사람이 한 명이라도 있으면 `post_move_delay` 지점에서 하드 게이트; AI만 있는
    관전용 방은 기존처럼 짧은 sleep 후 자동 진행). 이걸로 "내가 이겼을 때만
    트릭이 보이던" 타이밍 버그를 근본적으로 해결.
  - 플레이어가 참가 시 좌석 번호(= Gomoku의 흑/백)를 직접 고를 수 있는 좌석 선택
    화면 추가 (`GET /api/rooms/{code}`로 좌석 현황 조회 후 선택).
- 부수적으로 발견해 고친 버그: `NEVER_WIN_COLOR` 과제가 한 번도 위반 안 됐어도
  게임 종료 시 강제로 실패 처리되던 것(`force_resolve_if_unresolved_at_end`의
  catch-all이 이 케이스를 잘못 잡아먹음), `describe()`가 dict 리터럴 즉시 평가
  때문에 다른 과제 종류를 설명할 때도 죽던 것.
- 전체 pytest 59개 통과 확인, 브라우저에서 드래프트 → 트릭 진행 → "다음" 게이팅
  → 게임 종료까지 실제로 플레이해 검증.

### 명시적 확인/준비 단계로 트릭 사이 흐름 재설계 (2026-08-09)

기존에는 트릭 사이 일시정지가 `post_move_delay`라는 GUI 페이싱 휴리스틱(트릭이
막 끝났고 사람이 있으면 정지)에 불과했고, 통신 가능 여부는 `trick_in_progress`가
비어있는지로 추론했음. 이 때문에 (a) 트릭 1은 과제 드래프트 직후 바로 시작돼서
`post_move_delay`가 적용 안 되고 리더가 AI면 통신 기회 없이 즉시 첫 카드가
나가버리는 문제, (b) 트릭 경계에서 "다음"을 누르기도 전에 통신 가능 상태가
잠깐 열렸다 닫히는 레이스가 있었음.

과제 드래프트처럼 명시적인 `GameState.phase`로 다시 모델링: 매 트릭 시작 전
(트릭 1 포함) `"trick_ready"` 단계로 들어가고, 각 좌석이 개별적으로
`mark_ready()`를 호출해야 함 — 전원이 준비되어야 `"playing"`으로 넘어가 실제
카드를 낼 수 있음. `communicate()`는 이제 `phase == "trick_ready"`이면서
아직 준비를 선언하지 않은 좌석에게만 허용 — "트릭 도중에 통신이 다시 가능해지는"
버그가 애초에 발생할 수 없는 구조가 됨. MCTS 트리 탐색(`mcts.py`)과 self-play/
evaluate/CLI는 통신을 학습된 결정으로 다루지 않으므로 `GameState.auto_ready_up()`
으로 이 구간을 그냥 건너뜀.

GUI: 트릭이 끝나면 "확인"(카드 목록 clear, 서버 왕복 없이 순수 클라이언트
동작) → 통신 가능 카드에 토큰 표시 + "준비" 버튼 → 전원 준비되면 자동으로 다음
트릭 시작. 누가 준비했는지 각 플레이어 보드 밑에 ✅로 표시.

또한 👑(사령관, 게임 내내 고정 — 드래프트 순서를 정한 사람)과 ▶(이번 트릭 리더,
트릭마다 승자로 바뀜)를 분리 — 기존엔 `current_leader` 하나로 둘 다 표시해서
트릭 1 이후엔 사령관이 아닌 사람도 왕관을 달고 있는 것처럼 보였음. `GameState`에
`commander` 필드 추가.

  직접 재현 테스트(중간에 위반한 경우, 마지막 트릭에 위반한 경우 둘 다) 결과
  버그를 찾지 못함 — `NEVER_WIN_COLOR` 위반 시 해당 즉시 `outcome=False`로
  확정되고 `player_to_act`가 `None`이 되어 게임이 바로 멈추는 것을 확인함.
  실제로 미션을 어겼다면 지금 동작(실패로 표시)이 맞는 것으로 보임 — 재현되면
  위 게임 로그를 남겨서 다시 확인.

### Gomoku 자기대국 속도 최적화 (2026-08-09)

15×15 재학습을 시작하기 전에, CPU에서 시뮬레이션 100회 기준 자기대국 한 판이
755.8초로 비정상적으로 느린 것을 확인하고 cProfile로 실측 조사함 (GPU는 이
컴퓨터에 NVIDIA GPU 자체가 없어서(내장 그래픽뿐) 애초에 선택지가 아니었고,
어차피 병목이 렌주 판정이라는 순수 파이썬 로직이라 GPU로 옮겨도 도움 안 됐을
부분).

- 전체 시간의 ~67%가 `Board.is_forbidden_for_black`(렌주 금수 판정)에서 소모.
- `legal_moves()`가 노드당 **두 번** 호출되고 있었음: `_expand()`가 자식을 만들
  때 한 번, `net.predict()` 안의 `legal_action_mask()`가 같은 보드에 대해 또
  한 번 — 완전히 같은 비싼 계산을 중복 수행. 한 번 계산해서 재사용하도록 수정
  (`legal_action_mask_from_moves` 추가, `predict(board, legal_moves=...)`).
- MCTS가 시뮬레이션 예산(예: 100회)과 무관하게 매 확장마다 **모든** 합법수의
  자식 보드를 즉시 clone+착수하고 있었음 (빈 보드 초반엔 합법수가 200개 넘음).
  대부분 한 번도 방문되지 않고 버려지는 계산이었음 — `Node.ensure_board()`로
  지연 생성하도록 변경, PUCT가 실제로 그 자식을 선택했을 때만 보드 생성.
- 렌주 판정 로직 자체는 손대지 않음(정확성 그대로, 테스트 70개 통과) — 순수
  중복/낭비 제거. 같은 벤치마크로 재측정: **755.8초 → 238.6초 (약 3.2배)**.
- 참고용 추정치: 기본 설정(`games-per-iter=20`)이면 자기대국만으로 iteration당
  약 80분(20 × 238.6초) — 여전히 길지만 재학습을 현실적인 범위로 당겨줌.

### Gomoku 자기대국 2차 최적화 + 병렬화 + 재학습 시작 (2026-08-09)

사용자가 추가 최적화 여지와 PyPy 사용 가능성을 물어봐서 다시 cProfile로 실측:

- 이전 라운드에서 "중복 계산 제거"는 끝냈지만, 여전히 시간의 91%가
  `renju.classify_black_move`(렌주 금수 판정) 내부에서 소모되고 있었음. 그 안에서도
  `_has_open_four_span`이 단일 최다 호출 함수(17만+회) — `_is_open_three_through_zero`가
  후보 빈 칸마다 `dict(values)`로 딕셔너리 전체를 복사하고, 매 윈도우 검사마다
  `any()`/`all()` 제너레이터를 새로 만드는 게 파이썬 인터프리터 오버헤드의 대부분이었음.
  - 오프셋→값 표현을 `dict`에서 리스트(오프셋+PAD로 직접 인덱싱)로 교체.
  - 가상 착수 검사(`_is_open_three_through_zero`)를 딕셔너리 복사 대신 리스트 한 칸을
    임시로 바꿨다 되돌리는 방식으로 변경(복사 자체를 없앰).
  - `any()`/`all()` 제너레이터를 명시적 언롤 루프/조건문으로 교체.
  - 판정 로직/의미는 전혀 바꾸지 않음 — `tests/gomoku/test_renju.py` 14개 전부
    그대로 통과. 같은 벤치마크(시뮬레이션 100회 자기대국 한 판): **238.6초 → 44.4초
    (추가 5.4배, 1차 최적화 포함 원래 대비 약 17배)**.
- **PyPy는 이 프로젝트엔 못 씀**: 확인해보니 PyTorch는 PyPI에 CPython 전용 wheel만
  올라옴(`cp312` 태그만 존재, `pp3xx` 태그 없음) — PyPy 자체를 지원하지 않고, 소스
  빌드도 사실상 비현실적(대규모 C++/CUDA 확장이 PyPy의 cpyext 호환 레이어를 감당 못함).
  렌주 판정처럼 순수 파이썬 로직이라 PyPy면 이론상 도움 될 부분이었지만, torch 의존성
  때문에 애초에 선택지가 아님.
- **자기대국/아레나 게임을 프로세스 풀로 병렬화**: 게임 하나하나가 서로 독립적인데도
  지금까지 한 프로세스에서 순차 실행 중이었음. CPU는 물리 코어 4개(논리 8개, i5-8250U)
  — `ProcessPoolExecutor`로 `games_per_iter`개 게임을 동시에 굴리도록 `train.py`/
  `evaluate.py`에 워커 풀 추가(`--workers`, 기본 4). 각 워커는 `torch.set_num_threads(1)`로
  고정해서 프로세스끼리 스레드를 겹쳐 쓰다 오히려 느려지는 걸 방지. `nn.Module`은 프로세스
  경계를 안전하게 못 건너므로 `state_dict()`만 넘겨서 워커 안에서 재구성.
  실측(시뮬레이션 100회, 8게임): 워커 1개 366.1초 → 워커 4개 154.1초 (게임당 환산
  약 2.4배; 물리 코어 4개 대비 완전한 4배는 아니지만 유의미한 이득).
- 두 최적화를 합치면 이번 재학습 라운드는 최초 측정치(755.8초/판) 대비 게임 생성
  처리량 기준 약 39배 빠른 상태로 시작.
- 위 최적화를 마친 뒤 실제로 15×15 재학습 실행: `--iterations 30 --games-per-iter 20
  --num-simulations 100 --arena-games 12 --arena-simulations 80 --workers 4 --seed 42`.
  약 4시간 48분 소요(iteration당 평균 ~9.6분 — 병렬화에도 불구하고 예상보다 느렸음,
  아레나 검증까지 포함된 시간이라 자기대국 벤치마크 단일 수치보다는 항상 더 걸림).
  30 iteration 중 8회 승격(iter 1,2,5,8,11,23,24,25,30), 마지막 iter 30에서도 승격
  (cand=9 inc=3). policy_loss 4.594→3.289로 꾸준히 감소; value_loss는 뚜렷한 하향
  추세 없이 0.53~0.79 사이에서 오르내림(초반 iteration 학습에서 흔한 패턴, 계속
  지켜볼 부분). `checkpoints_gomoku/best.pt`로 랜덤 상대 평가(20게임, 시뮬레이션
  100회): **20승 0패 0무 (100%)** — 기초 실력은 확실히 학습됨. 상대가 랜덤이라 이
  결과 자체는 실력의 상한을 말해주진 않음; 다음엔 이전 체크포인트나 사람 상대로
  더 의미 있는 평가가 필요.

### Gomoku GPU 재설계 (2026-08-11)

다른 랩탑에서 진행하던 프로젝트를 RTX 3060(12GB VRAM, driver 560.94, CUDA 12.6,
PyTorch 2.6.0+cu124) 머신에 clone해서 이어감. Python은 아예 안 깔려있어서(Windows
Store 스텁만 존재) winget으로 Python 3.12 설치부터 시작, `pip install -e ".[dev]"`로
프로젝트 의존성 설치, `torch.cuda.is_available()` + GPU matmul로 CUDA 동작 확인,
기존 테스트 70개 통과 확인 후 재설계 착수.

기존 모델(conv 3층·64채널·non-residual, CPU 학습 전제로 일부러 작게 설계)과 self-play
구조(MCTS가 게임 하나·리프 하나씩 순차적으로 신경망 호출, batch size 항상 1)로는
GPU를 붙여도 이득이 없다는 게 `docs/AI_STRATEGY.md`에 이미 명시돼 있었음 — 그 문서의
열린 TODO였던 "GPU 배치 self-play 리팩터링"을 실행:

- **모델**: `PolicyValueNet`을 10-block residual tower·128채널(~5M 파라미터)로 교체
  (`network.py`). `channels`/`num_blocks` 계속 생성자 인자로 조절 가능.
- **배치 MCTS**: `mcts.py`에 `run_mcts_batch(boards, net, ...)` 추가 — 여러 게임의
  트리를 락스텝으로 진행시키며, 매 시뮬레이션 라운드마다 리프 평가가 필요한 보드들을
  한 번의 forward pass로 묶어서 처리. 기존 `run_mcts`는 `run_mcts_batch([board], ...)`의
  얇은 래퍼로 남김(사람 대전용, 처리량 신경 안 써도 됨).
- **배치 self-play/arena**: `self_play.py`의 `play_self_play_games_batch`가 여러 게임을
  동시에 진행시키며 매 수마다 배치 MCTS 한 번 호출. `evaluate.py`의 아레나도 같은
  방식으로 재작성 — 한 게임 안에서는 각 색이 항상 자기 자신의 네트워크로만 탐색해야
  하므로, 매 수마다 "지금 candidate 차례인 게임들"과 "incumbent 차례인 게임들"을 나눠
  각각 배치 호출. 기존 `ProcessPoolExecutor` CPU 멀티프로세싱 경로(`--workers`)는
  제거 — GPU/CPU 둘 다 같은 배치 코드 경로 사용 (`--device auto|cuda|cpu`).
- **체크포인트 포맷**: `{"config": {...}, "state_dict": ...}`로 변경 — 로더가 저장된
  config로 정확한 모양의 네트워크를 재구성(`save_checkpoint`/`load_checkpoint`,
  `ai.py`/`cli.py`/`evaluate.py`/`train.py` 전부 이걸로 통일). 옛 포맷 체크포인트는
  로드 시 명시적으로 예외 발생(자동 마이그레이션 없음) — 어차피 로컬에 남은 체크포인트가
  없어서 문제 없었음.
- **Elo 래더**: `elo.py`(표준 Elo 갱신식, K=32) 추가. `train.py`가 매 iteration의
  candidate-vs-incumbent 아레나 결과로 진행 중인 레이팅을 갱신해
  `checkpoints_gomoku/elo_ratings.json`에 iteration별 이력 기록. `gomoku-eval
  --checkpoint A --vs-checkpoint B`로 임의의 두 체크포인트 1회성 비교도 가능. 기존
  RandomPlayer 승률만으로는 "인간보다 강함"을 뒷받침 못 했던 문제를 겨냥한 것 —
  단, 이 레이팅은 프로젝트 자체 체크포인트끼리의 상대 비교치이지 외부 Elo 풀과
  보정된 값은 아님.
- **디스크 정리**: `train.py`에 `--keep-last-n`(기본 5) 추가 — `iter_XXXX.pt` 스냅샷을
  최근 N개만 남기고 정리(`best.pt`/`latest.pt`는 항상 유지). 기존 TODO였던 체크포인트
  보존 정책 정리 겸함.
- 테스트: `test_mcts.py`에 배치 MCTS 테스트 추가, `test_network.py`(체크포인트
  라운드트립), `test_elo.py` 신규 — 전체 79개 통과. 아직 실제 GPU 학습 런은 미실행.

### Gomoku 프로파일링 기반 2차 최적화 + 실제 학습 런 착수 (2026-08-11)

GPU 배치 self-play를 구현한 직후, 실제로 GPU가 얼마나 쓰이는지 cProfile로 실측
(64게임·시뮬레이션 100회 자기대국 배치, `PolicyValueNet(channels=128, num_blocks=10)`):

- **신경망 forward pass는 전체 1296.8초 중 14.9초(1.1%)뿐** — 배치화 자체는 의도대로
  작동, GPU 쪽은 병목이 아니게 됨.
- **`board.legal_moves()`(렌주 금수 판정) 계열이 840.5초(65%)** — `is_forbidden_for_black`
  2954만 회, `renju.classify_black_move` 이하 순수 파이썬 함수 호출. `board.py`를 다시
  읽어 White 차례엔 이 검사를 아예 안 하는 것(버그 아님)까지 확인 — 규칙상 당연한
  비용이지 낭비가 아니었음.
- **`.cpu()` 동기화가 242.1초(18.7%)** — 매 시뮬레이션 라운드마다 GPU→CPU로 결과를
  당겨오는 오버헤드. 그 다음은 `action_to_index` 등 자잘한 파이썬 오버헤드.
- 결론: "배치 self-play로 GPU를 쓴다"는 방향 자체는 맞았지만, 정작 이 게임에서 GPU가
  거의 기여할 게 없다는 것도 같이 확인된 셈 — 진짜 병목은 여전히(2026-08-09 라운드
  때와 마찬가지로) CPU 순수 파이썬 렌주 판정. **그래서 self-play/arena 게임 생성을
  다시 CPU `ProcessPoolExecutor` 멀티프로세싱으로 되돌리되(`train.py`/`evaluate.py`에
  `_self_play_worker`/`_arena_worker` 재도입), 각 워커 프로세스 내부에서도 배치 MCTS를
  쓰게 해서 두 최적화를 합침** — CPU 코어 분산 + 배치화로 인한 파이썬 오버헤드 절감을
  동시에 가져감. GPU는 학습 gradient step에만 사용(TF32 + `cudnn.benchmark` 켬).
- **워커 수 스윕**(24게임·시뮬레이션 60회, 물리 코어 14개/논리 코어 20개 머신): 1→4→8→
  12로 갈수록 뚜렷이 빨라지다가 12 이후로는 측정이 노이즈성으로 흔들림(게임 길이가
  랜덤이라 실행마다 총 작업량 자체가 달라져서 완벽히 통제된 비교는 아니었음). 로지컬
  코어 수(20)까지 밀어붙인 시도는 오히려 이전보다 느리게 나오기도 함 — 하이퍼스레드가
  이 워크로드엔 도움이 안 된다는 이전 라운드(2026-08-09) 관찰과 일치. **기본값을 12로
  설정**(`DEFAULT_SELF_PLAY_WORKERS`, `min(12, cpu_count-2)`).
- `encoding.py`의 `encode_board`도 셀당 파이썬 루프를 numpy 벡터 연산으로 교체(작은
  개선).
- 실측 1개 iteration(games-per-iter=64, sims=100, arena-games=12, arena-sims=80,
  workers=12): self-play 생성 698.9초 + 아레나 155.8초 ≈ 14분13초. 같은 조건에서
  self-play만 단일 프로세스로 돌리면 1296.9초였으니, 아레나 시간까지 포함해도 워커
  12개가 유의미하게 더 빠름(다만 이론적 12배엔 한참 못 미침 — 코어 전체 부하 시
  터보 클럭 하락, 게임 길이 편차로 인한 워커 간 불균형 등이 원인으로 추정, 정밀 분석은
  안 함).
- 이 시간 기준으로 6시간에 맞춰 `--iterations 24 --games-per-iter 64
  --num-simulations 100 --arena-games 12 --arena-simulations 80 --self-play-workers 12
  --device cuda --seed 42`로 실제 학습 런 시작(`checkpoints_gomoku/`, 기본 경로 —
  웹 앱의 `get_shared_net()`이 자동으로 집어감).
- **삽질 기록**: 매뉴얼로 `nohup ... & disown`한 백그라운드 프로세스가 이 에이전트
  환경의 셸 세션 경계를 못 넘기고 죽는 걸 확인(Windows/샌드박스 특성으로 보임) —
  대신 에이전트 툴 자체의 `run_in_background` 메커니즘을 써야 세션을 넘어 계속 살아있음.
  중간에 `tasklist //FI "IMAGENAME eq python.exe"` 필터 구문이 이 git-bash 환경에서
  깨져서 실행 중인 프로세스를 계속 "없음"으로 잘못 보고하는 바람에 멀쩡히 도는 학습을
  두 번이나 오판해서 죽였음 — `tasklist | grep -i python`처럼 필터 없이 걸러야 신뢰 가능.
  또한 시스템이 절전 모드로 들어가면 어떤 방식으로 백그라운드 실행했든 전부 죽으므로,
  긴 학습 런 전엔 `powercfg /change standby-timeout-ac 0`(+ dc)로 절전을 꺼둬야 함
  (노트북 뚜껑을 닫으면 이 설정과 무관하게 강제로 절전에 들어갈 수 있으니 별개로 주의).

**학습 결과** (24 iteration, 실제 소요 약 5시간 24분 — iteration당 평균 gen_time
~620초 + arena_time ~148초): 승격은 **iter 3, iter 12 단 2회뿐**(24개 중 8.3%,
2026-08-09 CPU 소형 모델 런의 8/30=26.7%보다 낮음). `best.pt`는 iter 12 시점 가중치로
고정된 채 이후 12번 더 rejected. `policy_loss`는 24 iteration 내내 3.89~3.91 사이에서
거의 안 움직였고(초반 3.910→막판 3.905), **`value_loss`는 0.572→0.906으로 오히려
계속 상승** — 이건 좋은 신호가 아님, 가치망이 수렴이 아니라 발산/과적합 방향으로
가고 있다는 뜻. 원인 후보(확인 안 됨, 다음 런에서 조정 필요): (a) lr=1e-3이 이 정도
용량(320만 파라미터)의 네트워크엔 너무 큼, (b) `--games-per-iter 64`로 모은 데이터
대비 `--epochs-per-iter 10 --batch-size 256`이 버퍼를 너무 자주/오래 재사용해서 최근
데이터에 과적합, (c) AMP(TF32/fp16 autocast)가 가치망 학습에 불안정성을 더함. Elo도
1000→1208로 올랐지만 이 지표 자체가 "매번 새로 만든 candidate를 (대부분 이기는)
incumbent"만 상대하는 구조라 — 실제로 붙는 상대가 계속 candidate 자기 자신의 근친
버전뿐이라 절대적 실력 향상 없이도 위로 드리프트할 수 있음(문서 상단 Elo 래더 설명의
한계 그대로). **`best.pt`(iter 12) vs `iter_0024.pt` 직접 대결(20게임, 시뮬레이션
150회)로 검증**: best.pt가 14승 6패로 우세 — 게이트키핑이 제대로 작동해서 더 약한
후반 iteration들을 실제로 걸러냈다는 뜻이므로, "최종 iteration이 아니라 best.pt를
쓴다"는 설계가 이번에도 유효했음을 확인. `best.pt` vs RandomPlayer(30게임, 시뮬레이션
200회): 30승 0패 — 예상대로 상한 확인용 사인 체크일 뿐, 이 자체로 실력을 말해주진
않음. **결론**: 파이프라인 자체는 정상 작동(배치 self-play, 멀티프로세싱, 게이트키핑,
체크포인트, Elo 로깅 전부 크래시 없이 24 iteration 완주) 하지만, `value_loss` 상승
추세로 볼 때 하이퍼파라미터 튜닝(특히 학습률, epochs_per_iter/batch_size 비율) 없이
그냥 더 오래 돌리는 것만으로는 이 네트워크 크기에서 안정적으로 강해지지 않을 수 있음
— 다음 런 전에 점검 필요.

**`value_loss` 발산 원인 확정 및 수정 (2026-08-11)**: 코드를 다시 읽어서 근본 원인을
찾음 — 위에서 나열한 하이퍼파라미터 후보들이 아니라 **훈련 루프 설계 자체의 버그**였음.
`optimizer = torch.optim.Adam(net.parameters(), lr=lr)`는 루프 밖에서 딱 한 번
생성되는데, arena에서 rejected될 때마다 `net.load_state_dict(best_net.state_dict())`로
가중치 값만 `best_net` 걸로 되돌리고 있었음(이 리셋 로직 자체는 이번 재설계 이전부터
있던 기존 코드). 문제는 `load_state_dict`가 파라미터 텐서의 **값만** 덮어쓸 뿐, Adam이
파라미터별로 들고 있는 momentum(`exp_avg`)·분산 추정치(`exp_avg_sq`)·step 카운트는
그대로 남는다는 것 — 그래서 매 iteration마다 "지금 이 가중치가 밟아온 gradient
궤적"에 대해 옵티마이저가 잘못된 기억을 갖고 다음 스텝 크기를 계산하게 됨. 이번 런은
24개 중 22개가 rejected라 이 어긋난 상태가 12번 연속으로 누적됐고, 네트워크도 커져서
(32만→320만 파라미터) 영향이 두드러진 것으로 보임 — 왜 이전 CPU 소형 런(승격률 26.7%)
에서는 덜 두드러졌는지도 설명됨.

**수정**: candidate(`net`)를 reject돼도 더 이상 되돌리지 않음 — 원조 AlphaZero처럼
candidate는 계속 이어서 학습하고, `best_net`만(self-play/배포용) 게이트 통과 시에만
갱신. 가중치와 옵티마이저 상태가 항상 같은 궤적을 공유하게 되어 이 불일치가 원천
제거됨. `train.py` 모듈 docstring과 promote/reject 분기 갱신, 테스트 79개 재통과 확인.
재학습해서 `value_loss`가 실제로 수렴하는지 다음 런에서 확인 필요.

### Elo candidate/best 분리 + arena 색 배정 버그 발견 (2026-08-11)

사용자가 candidate 전용 Elo 레이팅을 요청 — `elo_state["current"]` 하나였던 걸
`candidate`(계속 학습되는 `net` 자체)와 `best`(게이트 통과한 `best_net`)로 분리.
매 iteration candidate가 자기 자신의 레이팅에서 시작해 갱신되도록 수정(이전엔 매번
`best`와 같은 값에서 시작한다고 가정 — reset-on-reject 제거 이후로는 이 가정이 점점
부정확해지고 있었음). 기존 `elo_ratings.json`(단일 `current` 키)도 자동 마이그레이션.

이 작업 중 사용자가 "다른 버그도 있는지 점검해달라"고 요청해서 전체 파이프라인을
코드 레벨로 다시 훑음 — **두 번째 진짜 버그 발견**: `evaluate.py`의 arena가 여러
게임을 배치/멀티프로세스 청크로 나눠 처리하도록 리팩터링되면서, 색 배정
(`a_color = [1 if g % 2 == 0 else -1 for g in range(num_games)]`)이 매 청크마다
`g=0`부터 다시 시작하고 있었음 — 원래(리팩터링 전) 코드는 `g`가 매치 전체를 도는
인덱스였을 때만 맞는 로직이었는데, 배치화하면서 이 전제가 깨진 걸 놓침.
`arena_games=12, self_play_workers=12`(6시간 런의 실제 설정)면 청크가 전부 1게임
짜리라 **candidate가 24 iteration 내내 arena 12게임 전부 흑을 뒀음** — 게이트키핑
판정의 통계적 타당성을 갉아먹는 실제 회귀. `start_idx`(매치 전체에서 몇 번째
게임인지)를 청크마다 넘기도록 고쳐서 수정, 재현 테스트(`test_evaluate.py`) 3개
추가. 렌주 룰 자체가 흑의 선공 이점을 상쇄하도록 설계돼 있어서 이전 런 결과에
미친 영향은 크지 않을 걸로 보이지만(버그 #1, 옵티마이저 불일치 쪽이 훨씬 크게
기여했을 것), 실제 버그였음.

### GPU 환경 재최적화: Numba + MCTS 트리 재사용 (2026-08-11)

"C++로 렌주 판정을 다시 짤까?"라는 질문에, 그보다 훨씬 저비용/저위험인 두 가지를
먼저 제안해서 승인받아 진행:

**1. Numba JIT.** `renju.py`는 2026-08-09 라운드에서 이미 dict 대신 plain list,
언롤된 루프로 다듬어져 있어서 Numba `@njit`에 이상적인 모양이었음. 대신 `Board.cells`를
`list[int]`에서 numpy `int8` 배열로 바꿔야 했음(그래야 매 호출마다 리스트를 통째로
복사/reflect하는 오버헤드 없이 zero-copy로 JIT 코드에 넘어감) — `board.py`(clone/
__post_init__/dataclass `eq=False`, numpy 배열 필드가 있으면 auto-`__eq__`가
"truth value of array is ambiguous"로 깨짐), `web_view.py`(`list(board.cells)`가
numpy 스칼라를 만들어서 JSON 직렬화가 깨짐 — `.tolist()`로 수정, 웹 UI 회귀 테스트는
없어서 직접 `json.dumps`로 확인) 같이 걸리는 곳도 손봄. `classify_black_move`의
공개 시그니처(`str | None` 반환)는 `web_view.py`/`app.js`/`test_renju.py`가 특정
문자열 값에 의존하고 있어서 그대로 유지 — 내부적으로만 int 코드를 반환하는 njit
함수를 두고, 얇은 Python wrapper가 문자열로 번역. **정확성 검증**: 기존 렌주
테스트 14개 + 원본(git show HEAD) 구현과 무작위 3000개 포지션 크로스체크로 전부
일치 확인 후 반영. **효과**: 같은 벤치마크(64게임·시뮬레이션 100회)가 1296.9초 →
400.4초(약 3.24배) — 렌주 관련 시간 비중이 65%→14%로 줄고, `.cpu()` 동기화(30%)와
`action_to_index`의 "r,c" 문자열 파싱(29%)이 새로운 병목으로 드러남(다음 라운드
후보로 기록만 해둠, 이번엔 손 안 댐).

**2. MCTS 트리 재사용.** 매 수마다 트리를 새로 만들지 않고, 실제로 둔 수의 자식
서브트리를 다음 수의 루트로 재사용(`mcts.py`에 상태를 갖는 `BatchedMCTS` 클래스
추가, 기존 `run_mcts_batch`/`run_mcts`는 이걸 감싸는 1회성 wrapper로 유지 — arena/
사람 대전 등 재사용이 필요 없는 호출자는 그대로 동작). **구현 중 자체 버그 두 개를
찾아서 고침**:
  - 1차 구현은 재사용 여부와 무관하게 매 수마다 `num_simulations`만큼 항상 "추가로"
    돌고 있었음 — 재사용의 핵심은 이전 탐색에서 이미 쌓인 visit을 감안해서 "부족한
    만큼만" 새로 도는 건데, 이걸 안 해서 벤치마크가 오히려 401.4초로 (거의) 그대로/
    더 느려짐. `num_simulations`를 "루트당 목표 총 visit 수"로 재해석하도록 수정.
  - 그 다음 버전은 "이미 쌓인 visit"을 새 루트의 **자식들**(손자뻘)의 visit 합으로
    계산했는데, 정작 필요한 건 새 루트 **자기 자신의** `visit_count`(구 트리에서
    자식이었을 때 실제로 몇 번 방문됐는지)였음 — 고쳤더니 이번엔 결정론적 A/B
    스크립트로 직접 계측(같은 net, 노이즈 없음, temperature=0이라 완전히 동일한
    수순 보장)해서 확인.
  - 마지막으로 발견한 구조적 한계: self-play가 여러 게임을 한 배치로 묶어 도는데,
    배치 전체에 "루트당 목표"를 하나의 공유 라운드 수로 적용하면 그 배치에서 가장
    적게 재사용된(운 나쁘게 노이즈로 인해 거의 안 방문된 수를 둔) 게임 하나 때문에
    배치 전체의 라운드 수가 거의 안 줄어듦 — 15x15 초반 보드는 합법수가 200개가
    넘어서 노이즈 낀 100회 시뮬레이션으로는 대부분의 수가 방문 1회 안팎에 그치는
    게 흔했음(직접 로깅해서 확인: `already` 값이 대부분 1, 가끔 20~40대). 배치
    전체가 아니라 **루트 하나하나가 독자적으로 자기 목표에 도달하면 그 루트만
    멈추도록** 시뮬레이션 루프를 다시 짬(다른 루트는 계속 진행) — 배치 내 최악의
    경우에 전체가 끌려가는 문제 해소.
  - **최종 효과**: Numba 단독(400.4초) 대비 375.1초로 추가 **6.3% 개선** — 기대했던
    것보다 훨씬 작음. 원인은 위에서 확인한 구조적 한계 그대로: 15x15 보드 특유의
    넓은 분기(초반 합법수 200+) + self-play의 Dirichlet 노이즈가 방문을 얇게
    퍼뜨려서, 재사용해도 캐리오버되는 visit 자체가 많지 않음. Numba(1296.9초→
    400.4초, 3.24배)와 합쳐 원래 대비 **총 3.46배**.
  - **적용 범위**: self-play에만 적용, arena는 그대로(양쪽 색이 서로 다른 net을
    쓰고 턴이 번갈아가며 바뀌는 구조라 재사용을 붙이면 "한 게임에 트리 두 개를
    양쪽 플레이어의 실제 수 진행에 맞춰 유지"해야 해서 복잡도가 확 늘어나는데,
    arena는 self-play보다 게임 수 자체가 훨씬 적어서 투자 대비 효과가 낮다고
    판단 — 필요해지면 다음에 고려).

### 재학습 캠페인(run1~8, 누적 1500 iteration) + self-play 붕괴 발견 및 수정 (2026-08-12~17)

**진행**: 버그 수정 후 새 checkpoint 계보로 처음부터 재학습 시작(기존 버그 있던
런은 `checkpoints_gomoku_buggy_20260811/`로 보존). 여러 차례 나눠서(70+80+40+149+
158+233+500 iteration) 누적 1500 iteration까지 진행. 매 런 종료 후 이전 스냅샷과
30게임(temperature=0.4) 맞대결로 실제 개선 여부를 확인하는 루틴을 정착시킴 — **짧은
구간(150 iteration 안팎)은 승격/거절 노이즈에 자주 묻히고, 300+ iteration 단위로
묶어야 추세가 뚜렷이 드러남**을 반복 확인(예: run5 단독 17:13, run6 단독 15:15로
각각 무의미해 보였지만 run5+run6 합산 460→767 구간은 25:5로 명확).

**부수적으로 고친 버그/추가한 기능**:
- `_prune_iter_checkpoints`가 파일명(`iter_XXXX.pt`의 숫자) 기준으로 정렬했는데,
  `run_training`은 재시작할 때마다 iteration 카운터가 1로 리셋되므로 새 런의
  `iter_0001.pt`가 이전 런의 `iter_0080.pt`보다 이름순으로 "더 오래된" 것으로
  취급되어 즉시 pruning됨 — 40-iteration 런 하나가 자기 스냅샷을 단 하나도 못
  남기는 실제 사고로 발견. mtime 기준 정렬로 수정, 회귀 테스트 추가.
- 재시작해도 총 iteration 수를 알 수 없던 문제 — `elo_ratings.json`의 `history`가
  매 iteration 정확히 1개씩 쌓이고 트리밍되지 않는다는 점을 이용해
  `len(elo_state["history"])`를 누적 총량의 근거로 삼아 로그에 노출(`total=N`).
- CPU 워커 수 재실측: Numba 적용 전 스윕(12에서 포화)이 stale해진 걸 확인 — 이
  머신(13세대 i5-13600KF, P-core 6×2 + E-core 8×1 = 물리14/논리20)에서 재측정하니
  **16에서 정점**(12 대비 처리량 +9%), 18~20은 다시 하락. 기본값 12→16으로 변경.
- `remote_selfplay.py` 신규: LAN 공유폴더를 통해 보조 PC(예: 상시 켜져 있는 저전력
  노트북)가 self-play 게임을 만들어 보태는 선택적 기능. 메인 학습 루프는 원격
  워커의 존재 여부와 무관하게 항상 동일하게 동작(opportunistic하게 주워담기만
  함, 절대 기다리지 않음) — 원자적 파일 쓰기(임시파일→rename)로 쓰다 만 파일
  문제 방지, 체크포인트에 iteration 태그를 달아 `--remote-max-staleness`보다
  오래된 배치는 폐기. 실사용은 보류(가용 PC의 CPU가 약해 이득이 작을 것으로 판단).
- `analysis_server.py` 신규: 수동으로 흑/백을 직접 둬보면서 정책망 prior 히트맵,
  가치망의 흑/백 관점 value, 100회 MCTS 후 visit_probs 히트맵을 동시에 보여주는
  별도 진단용 웹 도구(포트 8001, 기존 웹앱/GUI는 전혀 안 건드림).

**self-play 붕괴 발견**: run8(1000→1500) 진행 중 self-play 승패가 흑 58~64 : 백
0~6으로 극단적으로 쏠리고 value_loss가 0.4~0.5대에서 0.04~0.14대로 "붕괴"하듯
떨어지는 게 로그에서 눈에 띔. run8 종료 후 이전 스냅샷(1000번째)과 30게임
비교했더니 **13:17로 오히려 후퇴** — 87번 승격됐음에도 실제로는 약해짐.

원인 조사: 실제 self-play 재현(5회 독립 시행)에서 흑이 매번 4행에 5개를 나란히
쌓는 동안 **백이 단 한 번도 막으려 시도하지 않음**(전혀 무관한 칸에 착수, 매번
다른 칸이라 사실상 무작위)을 직접 확인. 처음엔 run8이 새로 만든 붕괴로 의심했으나,
**run8 이전(1000번째, "건강한" 것으로 여겨졌던) 체크포인트도 White로 같은 패턴을
전혀 못 막는 것**을 직접 재현해 확인 — 훨씬 이전부터 있던 방어 사각지대였고,
run8의 self-play가 그걸 더 적극적으로 우려먹으면서 비중이 극단화된 것으로 재해석.

**핵심 진단**: 왜 이게 게이트(arena)를 통과했는지 — arena는 매번 `candidate` vs
그 시점의 `best_net`인데, 둘 다 같은(이미 편향된) 계보에서 나오므로 "서로 비슷하게
나쁜 부분"은 상대 비교로 검출 불가. 왜 시뮬레이션을 늘려도 안 고쳐지는지 —
흑 3연속(`(4,5)(4,4)(4,3)`) 강제 국면에서 White의 막는 수 확률을 시뮬레이션 수별로
측정(`add_noise=True`, 실제 self-play와 동일 조건)했더니:

```
n=  100  block_mass=0.020
n= 500   block_mass=0.014
n=2000   block_mass=0.004   (더 나빠짐 — (12,10) 등 무관한 수에 41% 집중)
```

**시뮬레이션을 늘릴수록 오답에 대한 확신만 깊어짐** — 이건 tree-reuse 문서의
열린사 사례(prior가 낮아도 탐색을 늘리면 결국 찾아냄)와 정반대 패턴. 해석: PUCT
탐색은 가치망의 판단을 증폭할 뿐 교정하지 못하므로, 가치망 자체가 이 국면 부류를
잘못 평가하면 탐색은 그 오판을 더 깊이 파고들 뿐임. 근본 원인은 악순환으로 추정:
White가 막기에 계속 실패 → 학습 데이터에 "막았을 때 어떻게 되는지" 예제가 안 쌓임
→ 교정 신호 자체가 없음.

**조치**: (1) `mcts.py`/`self_play.py`/`train.py`에 `dirichlet_alpha`/`dirichlet_eps`를
CLI(`--dirichlet-alpha`, `--dirichlet-eps`)까지 전 구간 배선(멀티프로세스 워커
payload 포함), 기존 기본값(0.3/0.25)은 그대로 보존. (2) `best.pt`/`latest.pt`를
1000번째 스냅샷으로 롤백(`elo_ratings.json`의 총 iteration 카운트는 run8 기록을
남기기 위해 그대로 유지 — 가중치만 되돌리고 총 투입량 로그는 정직하게 보존).
(3) `--dirichlet-eps 0.5`(2배)로 30 iteration짜리 짧은 실험 런. 같은 진단을
재실행하니:

```
n=  100  block_mass=0.020
n=1000   block_mass=0.030
n=2000   block_mass=0.359   ((4,2)가 1등 후보로 등장, 방향 반전)
```

30 iteration만으로도 추세가 반전됨을 확인 — 다만 국면 하나에 대한 진단이라
과신은 금물, 더 긴 구간으로 재확인 필요. **후속 아이디어(미착수)**: 오목/렌주는
바둑과 달리 사(四)/삼(三) 같은 강제 수순이 국지적으로 뚜렷해서, 실제 강한
비신경망 렌주 엔진들은 이런 강제 라인을 전담으로 깊게 읽는 VCF/VCT류 위협-공간
탐색을 범용 탐색과 별도로 씀 — 지금 겪은 "막는 수를 prior가 아예 후보에서
누락시키는" 문제를 신경망 학습 신호 개선이 아니라 탐색 알고리즘 차원에서 보완하는
방법이 될 수 있음. 지금은 디리클레 노이즈 조정으로 먼저 대응 중이라 보류.

### run9 (dirichlet-eps=0.5, 500 iteration, 누적 1530→2030) 완료 + 진단 재확인 (2026-08-19~20)

중간에 Windows Update로 추정되는 예기치 않은 재부팅으로 프로세스가
`BrokenProcessPool`로 죽었음 (iteration 415/500, 총 1945에서 중단). 원인 조사:
`powercfg`로 절전 설정은 여전히 정상(꺼짐 확인)이었지만 `LastBootUpTime`이
마지막 체크포인트 저장 3.5분 후로 찍혀 있어 재부팅이 원인으로 확정. 데이터
손실은 없었음 (`iter_0415.pt`/`best.pt`/`latest.pt` 모두 안전) — 남은 85
iteration을 이어서 재개해 완료 (총 누적 2030).

**30게임 temperature=0.4 아레나 (run9 이후 best vs run9 시작 전 스냅샷)**:
18승 12패로 개선 방향이지만, 이 규모에서는 여전히 통계적으로 애매한 범위
(과거 15:15~18:12 관측과 유사) — 확실한 승리로 보긴 이름.

**block_mass 진단 재실행 (같은 강제 국면: 흑이 4행에 3-3-3 열린 삼, 백 차례)**:
30 iteration 테스트에서 봤던 `0.020→0.359` (n=100→2000) 반전은 이번 500
iteration 스케일에서는 **재현되지 않음**. run9 시작 전/후 체크포인트 모두
raw policy prior가 막는 수(4,2)/(4,6)에 ~1%만 할당하고, MCTS로 시뮬레이션
수를 늘려도(5개 시드 평균) block_mass가 대체로 1~2% 대에 머무름 — 뚜렷하고
일관된 개선 추세가 보이지 않음:

```
[pre-run9]  n=100: 0.008  n=400: 0.006  n=800: 0.005  n=2000: 0.144 (변동 큼)
[post-run9] n=100: 0.010  n=400: 0.024  n=800: 0.019  n=2000: 0.011
```

결론: 30-iteration 테스트에서 관측한 반전은 이 국면 하나에 대한 단일 시드
결과였고 (당시 문서에도 "과신은 금물, 재확인 필요"라고 적어뒀던 부분), 500
iteration 규모로 재확인해보니 재현되지 않았다 — 노이즈였을 가능성이 높음.
즉 dirichlet-eps 상향만으로는 이 특정 방어 사각지대가 durable하게 고쳐지지
않은 것으로 보임. 아레나 결과(18:12)는 전반적인 기력 향상 신호이긴 하지만
이 국지적 약점과는 별개일 수 있음. 다음에 시도해볼 만한 방향: (a) 이 국면을
self-play 학습 데이터에 강제로 더 자주 등장시키는 curriculum/replay 방식,
(b) 문서에 미착수로 남겨둔 VCF/VCT 위협-공간 탐색을 실제로 구현해서 강제
방어 수순을 탐색 알고리즘 차원에서 보완, (c) 이번 재부팅 크래시로 학습
로그 파일(run9 재개분)이 유실되어 self-play 흑/백 승률 추이를 크로스체크하지
못함 — 로그를 항상 안전한 경로에 남기도록 습관화 필요.

### 1수 앞 강제수 탐지(tactical_value) 추가 + 처음부터 재학습 (2026-08-21)

VCF/VCT 착수 전에, 훨씬 간단한 버전을 먼저 시도: `tactics.py`에
`find_winning_move`/`tactical_value` 추가 — 리프 국면에서 "지금 둘 차례인
쪽이 1수만에 이기는 수가 있는가", 없다면 "합법수를 뭘 두든 상대가 1수만에
이기게 되는가(=이미 진 상태인가)"를 정확히 계산해서, MCTS 리프 백업 시
신경망 value 추정치 대신 이 정확한 값을 사용하도록 `mcts.py`에 연결
(`search()`의 leaf backup 루프, `_batch_predict` 직후).

**주의할 점(사용자에게 미리 안내함)**: 이번에 진단했던 정확히 그 국면(백이
흑의 열린 삼을 막아야 하는 시점)은 이 함수 자체로는 "1수 필승/필패"가
아니라서 직접 잡히지 않음 — 열린 삼은 다음 수에 열린 사가 되어야 비로소
1수 필승 상태가 됨. 다만 MCTS가 "안 막았을 때" 라인을 몇 수 더 파고들면
2수 뒤(열린 사가 만들어진 시점)에서 정확한 값이 매겨지고, 이게 PUCT 백업을
통해 상위 노드(막을지 말지를 결정하는 지점)까지 전파되므로 간접적으로는
도움이 될 가능성이 있음 — 다만 검증된 바는 아니고 다음 재학습 결과로
확인 필요.

**성능 문제 발견 및 수정**: 첫 구현은 `Board._check_win`(순수 파이썬 루프)로
모든 빈 칸을 스캔 + 후보마다 `board.legal_moves()`를 다시 계산(불필요한
Renju 금지수 판정까지 재수행)해서 self-play가 2.6배 느려짐(5.46s/game →
14.26s/game, 8게임 기준 벤치마크). renju.py와 같은 방식으로 승리 판정
스캔을 numba `@njit`로 재작성(`_completes_win`/`_find_winning_move_jit`)하고
`legal_moves()` 중복 호출을 없앤 뒤 6.00s/game까지 회복 — 원래 대비 약
10% 오버헤드로 수용 가능한 수준.

`tests/gomoku/test_tactics.py` 8개 테스트 추가(승리수 탐지, 필패 판정,
렌주 장목(overline) 예외 처리 등). 전체 테스트 59개 통과.

기존 run1~9 누적 2030 iteration 체크포인트는
`checkpoints_gomoku_run1-9_archive_20260821/`로 백업(나중에 이번 방식으로
학습한 체크포인트들과 토너먼트 비교용). 이 변경만 단독 적용해서 처음부터
500 iteration 재학습 시작.

**위 "10% 오버헤드" 벤치마크는 오해의 소지가 있었음**: GPU 단일 프로세스
조건(`device='cuda'`, 배치 인퍼런스)에서 잰 숫자였는데, 실제 학습은
`--self-play-workers 16`으로 CPU 멀티프로세스 워커 각각이 단일 스레드로
도는 완전히 다른 조건. 실제 학습 로그로 확인해보니 1~3회차 gen_time이
858~952s, arena_time이 308~403s로, 이전 run들(같은 설정 기준 gen_time
550~700s, arena_time 130~175s)보다 self-play는 약 1.4배, arena는 약
2.3배 느렸음 — 3회차까지 일관되게 나타나 JIT 워밍업 같은 일회성 비용이
아니라 실제 지속 오버헤드로 확인. 500 iteration 전체를 이 속도로 돌리면
예전(~4~5일) 대비 ~7일까지 늘어날 것으로 추정되어, 학습을 중단하고 2차
최적화 진행.

**2차 최적화**: (1) `_find_winning_move_jit`이 보드 전체(size*size칸)를
스캔하던 걸, 이미 놓인 돌마다 4방향으로 `win_length-1`칸까지만 훑어
후보를 만드는 방식으로 변경 — 완성 가능한 5는 반드시 기존 돌에서
`win_length-1` 이내에 있어야 하므로 정확성 손실 없음. (2) 후보 칸마다
`cells[idx]=player`로 임시로 놓았다 되돌리던 부분을 제거 — `_completes_win`은
애초에 `(r,c)` 자체의 배열 값을 읽지 않고 그 바깥 이웃만 보므로 이 mutate가
전부 불필요한 코드였음. (3) `mcts.py`의 leaf backup에서, 이미 강제 결과가
확정된 리프는 신경망 forward pass 자체를 건너뛰도록 재구성 — 승리 국면은
찾아낸 필승수에 prior 전량을, 필패 국면은 균등 prior를 줘서 신경망 없이
바로 자식 노드를 만듦(`_expand_with_tactical_prior`).

결과: 1~2회차 gen_time 626.1s/762.9s, arena_time 150.9s/174.0s로 최적화 전
대비 거의 절반, 원래(tactics 적용 전) 역사적 기준치와 거의 동일한 수준까지
회복. 전체 테스트 59개 통과.

이후 사용자 요청으로 100 iteration 단위 체크포인트+테스트 청크 실행으로
전환해 재시작했으나("일단 이 정도에서 완료하고" 전까지는), 실전 학습을
더 돌리기 전에 코드 정리를 먼저 하자는 사용자 판단으로 학습을 전부 중단
(프로세스 킬)하고 3차 정리로 넘어감 — 아직 500 iteration 재학습은
실행하지 않은 상태.

**3차 정리 (코드 리뷰 기반)**: (1) 죽은 코드 제거 — `tactical_value`가
`mcts.py`에서 전혀 안 쓰이고(이미 `tactical_result`를 직접 호출) 테스트
에서만 참조되고 있어 삭제, docstring들도 같은 설명이 여러 곳에 중복돼
있던 걸 축약. (2) `find_winning_move`가 스캔 순서상 처음 찾은 필승수
하나에만 prior 1.0을 몰아주던 문제 발견 — 오픈 사처럼 필승수가 여러 개인
국면에서 이건 "가장 좋은 수"가 아니라 "구현상 우연히 먼저 스캔된 수"일
뿐이라, 나중에 이 국면이 실제 self-play 수순이 될 경우 학습 정책
타깃에 스캔-순서 편향이 섞임. `find_all_winning_moves` 추가(기존 스캔에
`early_exit` 플래그만 얹어 코드 중복 없이 구현)해서 발견된 모든 필승수에
prior를 균등 분배하도록 수정.

**4차 최적화: 슬라이딩 윈도우로 재작성**: 기존 방식은 "놓인 돌마다 앵커
삼아 주변 후보 스캔"이라 돌 개수 k에 비례해 계산량이 늘어남(종반에
불리). 대신 4방향(가로/세로/대각선 2개) 각 줄마다 길이 `win_length`
윈도우를 밀면서 "내 돌 개수/빈칸 개수"를 O(1)로 갱신(`_slide_line`) —
윈도우에 내 돌이 `win_length-1`개 + 빈칸 1개면 그 빈칸이 필승수. 흑
장목(overline) 예외는 윈도우 양 옆 칸이 내 돌이 아닌지 추가 확인으로
처리. 전체 비용이 돌 개수와 무관하게 O(size²)로 고정됨.

정확성 검증: 기존 60개 테스트 통과 + brute-force(모든 빈 칸에 직접
둬보고 `Board._check_win` 호출)와 300개 랜덤 국면(렌주 on/off 혼합) 대조
결과 완전 일치.

**성능은 기대와 달리 유의미한 개선 없음**: 8게임 벤치마크 기준 앵커
방식 3.47s/game vs 슬라이딩 윈도우 3.62s/game — 오차 범위 내로 거의
동일, 오히려 근소하게 느림. 15x15 오목은 실제로는 보드가 거의 안
채워진 채로 게임이 끝나는 경우가 대부분이라, "돌 개수에 비례"와 "보드
크기로 고정"의 점근적 차이가 실전 self-play에서는 잘 드러나지 않음.
알고리즘적으로는 더 견고한 접근(최악의 경우/종반 밀집 국면에 유리)이라
남겨두지만, 이번 최적화의 실질적 동기였던 "체감 속도 개선"은 이미 앞선
2차 최적화(NN 스킵 + mutate 제거)에서 대부분 달성된 상태였음.

### 렌주 쌍삼 판정 실버그 발견 및 수정 (2026-08-21)

이 최적화 작업과 별개로, 사용자가 실제 오목 화면 캡처를 보여주며 "쌍삼처럼
보이는 자리가 실제로는 금수가 아니다"라는 케이스를 제시 — `renju.py`가
이런 예외까지 감안하고 있는지 검증 요청. 확인 과정에서 진짜 버그를 발견함.

`_has_open_four_span`이 사(四)의 양쪽 플랭크 칸이 "비어있는지"만 확인하고,
그 플랭크를 채웠을 때 장목(6목)이 되는지는 확인하지 않고 있었음. 흑은
정확히 5개로만 이기므로(장목 무효), 플랭크 한 칸 너머에 이미 자기 돌이
있으면 그 플랭크는 채워봤자 진짜 승리가 아니라 금수(장목)가 되어 "가짜
위협"인데, 기존 코드는 이를 "진짜 열린 사"로 잘못 인정 — 결과적으로
어느 쪽으로도 실제 열린 사를 만들 수 없는 삼(한쪽은 장목, 한쪽은 백돌에
막힘)을 "쌍삼"으로 잘못 판정하는 사례가 있었음(`X..XX?.O` 패턴, 사용자
제시 케이스와 일치).

수정: `_has_open_four_span`에 "플랭크 한 칸 너머가 자신의 돌이 아님" 조건
추가. `_has_open_four_span`은 이 파일 전체 맥락상(백은 금수 없음) 항상
흑에 대해서만 호출되므로 별도 파라미터 없이 바로 적용 가능했음.

검증: 기존 62개 테스트 통과 + 이 버그와 무관한 독립 brute-force 판정기를
새로 작성(각 방향 완전탐색, "플랭크를 채우면 정확히 5인지" 직접 계산)해서
400개 무작위 국면(돌 뭉치를 만들어 삼/사 패턴이 잘 나오도록 유도)과 대조
— 전부 일치. 사용자 제시 케이스 및 변형(플랭크 직접 인접/2칸 떨어짐)을
회귀 테스트로 추가.

### 렌주 재귀적 금수 판정 구현 (완성 지점 자체가 금수인 경우) (2026-08-21)

같은 세션에서 사용자가 실제 대국 기보 캡처(37수째)를 제시 — "원래 3-3으로
못 놓을 자리인데, 완성 지점(G9)이 그 자체로 4-4 금수라서 3-3이 아니다"라는
케이스. 좌표를 여러 번 재구성하며 확인한 끝에(처음엔 제가 이미지를
잘못 읽어서 사용자가 직접 정정) 실제로 미구현된 규칙임을 확인.

**정의 정리**: "삼"이 되려면 (a) 한 수를 더해 열린 사를 만들 수 있어야
하고, (b) 그 한 수 자체가 흑에게 합법이어야 함(불가능한 수는 진짜 위협이
아님). 지금까지 코드는 사(四)의 플랭크가 합법인지(장목 아닌지, 지난
수정으로 커버됨)만 확인했지, "삼→사로 만드는 그 수 자체가 합법인지"는
확인하지 않고 있었음.

**구현**: `_classify_black_move_code`가 열린 사 후보를 발견하면, 그 완성
지점에 흑을 놓아보고 재귀적으로 자기 자신을 다시 호출해서 그 수 자체가
금수인지 확인(`check_completion_legal` 플래그, 재귀 호출 시 False로
넘겨서 1단계로 재귀 제한 — 실제 렌주 규칙 레퍼런스들도 보통 이 정도까지만
확인).

**numba 버그 2건 연쇄로 발견**: (1) 처음엔 별도 함수(`_is_open_three_
through_zero`)가 `_classify_black_move_code`를 부르고 그게 다시 그
함수를 부르는 상호재귀 구조로 짰는데, 실제 37수 국면에서 세그폴트 발생.
순수 파이썬으로 같은 로직을 이식해서 재실행해보니 3번 호출, 깊이 1로
정상 종료 — 로직은 맞고 numba의 문제로 판명. (2) 두 함수를 하나로 합쳐
자기 자신만 재귀하는 구조(self-recursion)로 바꿨는데도 여전히 세그폴트
— `cache=True`가 재귀 함수의 디스크 캐시와 상호작용하며 생기는 numba
버그로 확인(`cache=False`로 바꾸니 정상 동작). self-play 워커는 어차피
프로세스마다 새로 뜨므로 프로세스당 1회 재컴파일 비용 정도는 감수.

검증: 기존 63개 테스트 통과, 사용자 제시 실제 국면(37수) 정확히 재현해서
`None`(금수 아님)으로 정정됨을 확인. brute-force 판정기에도 같은 1단계
재귀 규칙을 추가해서 무작위 국면 1000개(일반 400 + 밀집 클러스터 600,
size 9~11)와 대조 — 전부 일치. self-play 벤치마크 재확인(4.26s/game,
`cache=False` 오버헤드 무시할 수준). 사용자 제시 실제 국면을 회귀
테스트로 추가.
